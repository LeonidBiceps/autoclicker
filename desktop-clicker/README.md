# МультиТул — desktop-версия автокликера

Тот же автокликер, но вне браузера: работает в любом окне и любой игре Windows, а не только на
вкладке Chrome. Electron + [@nut-tree-fork/nut-js](https://www.npmjs.com/package/@nut-tree-fork/nut-js)
для управления мышью/клавиатурой и [uiohook-napi](https://www.npmjs.com/package/uiohook-napi) для
записи реальных кликов (макросы).

**Готовый `.exe` для раздачи пользователям (без сборки):**
[MultiTool-2.8.0.exe](https://github.com/LeonidBiceps/autoclicker/releases/download/v2.8.0/MultiTool-2.8.0.exe)
— именно на эту ссылку указывает кнопка «Скачать МультиТул» в браузерном расширении
(`DESKTOP_APP_URL` в `extensions/clicker/options.js`). При новом релизе — залить новый `.exe` через
`gh release create vX.Y.Z ...` и обновить эту ссылку в двух местах: тут и в `options.js`.

## Запуск

```bash
npm install
npm start
```

Первая установка ставит Electron и пересобирает нативный модуль nut-js под версию Electron
(`electron-rebuild`, автоматически через `postinstall`) — может занять пару минут. `uiohook-napi`
пересборки не требует — у него уже есть готовый бинарник под Windows (N-API, ABI-стабильный).

## Сборка портативного .exe

```bash
npm run dist
```

Собирает через `electron-builder` в `dist/` — **протестировано end-to-end в этой сессии**: сборка
проходит, `.exe` (≈76 МБ) реально запускается и открывает окно. Сам скрипт (`scripts/build-obfuscated.js`)
обфусцирует `main.js`/`license.js`/`keymap.js`/`store.js`/`preload.js`/`pick-preload.js` перед сборкой
и **всегда** возвращает читаемый исходный код обратно после (даже если сборка упала) — проверено и на
успешном прогоне, и на упавшем. Если что-то прервёт процесс совсем грубо (например, вырубят
электричество) и рядом останутся файлы вида `main.js.bak` — значит откат не доехал, восстанови их
вручную (`.bak` → без расширения) или удали, если файлы и так на месте.

Если нужна сборка без обфускации (для отладки) — `npm run dist:raw`.

## Что умеет

**Бесплатно:**
- **Загрузочный экран** — маленькое окно с логотипом и спиннером на время старта (нативные модули
  вроде nut-js/uiohook подключаются не мгновенно), закрывается само, как только готово основное
  окно. Не показывается при тихом автозапуске в трей.
- Клик под курсором или в выбранной точке экрана — окно выбора точки работает на **любом мониторе**
  (крестик растягивается по всем подключённым экранам)
- Режим клавиатуры — **захват произвольной клавиши** («Установить клавишу» → жмёшь что угодно на
  клавиатуре, оно и запоминается), а не только фиксированный список. Работает через отдельную
  таблицу соответствия кодов клавиш между `uiohook-napi` (запись) и `nut-js` (воспроизведение) —
  `keymap.js`
- Интервал + разброс по времени — **слайдеры** с точным числовым полем рядом. Реальная скорость
  клика теперь честно соответствует слайдеру — раньше `nut-js` добавлял скрытую паузу перед КАЖДЫМ
  кликом (`mouse.config.autoDelayMs`, по умолчанию 100мс — предназначено для «более человечного»
  ввода, но тут автоматизация, не ручной ввод) и ещё бо́льшую перед каждым нажатием клавиши в режиме
  клавиатуры (`keyboard.config.autoDelayMs`, 300мс на pressKey **и** ещё 300мс на releaseKey). Из-за
  этого выставленные на слайдере 10мс на деле оборачивались в ~110мс (а для клика клавишей — вообще
  ~610мс), особенно заметно при клике по нескольким точкам подряд. Обе паузы теперь обнулены при
  старте приложения.
- **Глобальные хоткеи по-настоящему глобальные** — `globalShortcut` Electron перехватывает их в любом
  окне ОС, не только когда открыто окно приложения
- Автостоп по кликам/времени
- **Счётчик кликов поверх экрана** — маленький HUD в углу, пока кликер активен, виден поверх любой
  игры/программы
- **Запуск при старте Windows**, с опцией «не показывать окно при автозапуске» (сразу в трей)
- Трей-иконка — можно свернуть окно, приложение продолжает работать, доступ через иконку в трее
  (показать окно / старт-стоп / **перезапустить** / выход). При первом сворачивании в трей — одно
  уведомление, что приложение никуда не делось и как закрыть совсем. Защита от повторного
  запуска (`app.requestSingleInstanceLock`) — второй запуск `.exe`, пока первый уже работает,
  просто показывает существующее окно вместо ещё одной параллельной копии в фоне
- Постоянный сайдбар слева (Главная / Клик / Хоткеи / Макросы / Бинды / Профили / Автозагрузка /
  Текст с экрана / Запись экрана / Журнал / Настройки) — клик по пункту показывает эту страницу
  целиком справа, старт/стоп и статус остаются видны в сайдбаре независимо от того, какой раздел
  открыт. Главная страница — про Pro-версию и донат, отдельно от остальных настроек. Подсказки
  (ⓘ, `title` на полях) на менее очевидных настройках
- **Проверка обновлений** — при запуске тихо сверяется версия с последним релизом на GitHub; если
  вышла новая — на Главной появляется ненавязчивая строка-ссылка (просто открывает страницу
  релиза, ничего не скачивает и не ставит сама)
- **Журнал активности** — вкладка «Журнал»: короткая история значимых событий (старт/стоп кликера
  и т.п.) с временем — последние 100 записей, для отладки автоматизации, если не смотрел на экран
- **Автозагрузка** — вкладка «Автозагрузка»: список программ, которые запускаются вместе с Windows
  (из `HKCU\...\CurrentVersion\Run` и папки автозагрузки текущего пользователя), с переключателем
  включить/выключить у каждой. Выключение не удаляет запись — реестровые записи переносятся в свой
  раздел `HKCU\Software\МультиТул\DisabledRun`, ярлыки переименовываются в `*.lnk.disabled` — и то,
  и другое полностью обратимо. Не требует прав администратора и **не видит** записи «для всех
  пользователей» (`HKLM`, общая папка автозагрузки) — это осознанное ограничение, чтобы не требовать
  повышения прав. Тоже не тот механизм, что использует сам Task Manager (у него свой недокументированный
  формат для пометки «выключено») — переключатель здесь не отразится в Task Manager и наоборот.
- **Анти-АФК** — вкладка «Настройки»: раз в заданный интервал (по умолчанию 45 сек) курсор
  сдвигается на 1px и сразу обратно — не даёт сработать статусу «отошёл» или блокировке экрана.
  Реальная позиция курсора никуда не съезжает, двигается только сам факт движения.
- **Привязка к окну** — вкладка «Клик»: указываешь часть заголовка окна (вручную или кнопкой «Взять
  активное окно» — жмёшь, за 3 секунды переключаешься на нужное окно Alt+Tab'ом, заголовок
  подхватывается автоматически) — клики срабатывают, только пока это окно активно. Пусто — работает
  всегда, как раньше.

**Pro:**
- **Турбо-режим** — вкладка «Клик», раздел «Скорость»: галочка, которая полностью игнорирует
  интервал и разброс — кликает так быстро, как позволяет само железо (планирование следующего клика
  без задержки таймера вообще, вместо `setTimeout(delay)`). Слайдеры интервала/разброса гаснут,
  пока включено — они всё равно не участвуют. Проверено вживую: на тестовой машине минимальный
  интервал (10мс) после починки `autoDelayMs` (см. выше) давал ~34 клика/сек, турбо-режим — ~41
  клик/сек — честно, но не безгранично: настоящий потолок здесь не JS-таймер, а сама операция клика
  (перемещение курсора + нажатие через `nut-js`, реальный системный вызов ОС на каждый клик). Гейтинг
  на Pro проверен и на стороне главного процесса, не только в интерфейсе — если лицензия невалидна,
  настройка `turboMode` в файле настроек просто игнорируется.
- **Автостарт при простое** («обратный анти-АФК») — вкладка «Настройки»: запускает кликер сам,
  когда компьютером никто не пользуется дольше заданного порога (`powerMonitor.getSystemIdleTime()`,
  штатный Electron API). Для дальнего фарма — ушёл из-за компьютера, автоматизация подхватила сама.
  Срабатывает один раз за период простоя (не перезапускается раз в 5 секунд, пока стоит), взводится
  заново только после реальной активности
- **Уведомления в Telegram** — вкладка «Настройки»: сообщение о старте/остановке кликера в свой
  Telegram-чат через обычный Bot API (без библиотек). Токен бота — от @BotFather, ID чата — через
  `getUpdates` (подсказка прямо в интерфейсе). Кнопка «Отправить тест» проверяет настройку сразу
- без лимита кликов за один запуск (бесплатно — 5000 кликов, дальше стоп)
- разброс позиции клика
- **триггер по цвету** — кликает не по таймеру, а только когда цвет пикселя в выбранной точке
  экрана совпал с заданным (с настраиваемым допуском). Для игр: фарм ресурса, который появляется
  не всегда, рыбалка (клюёт → цвет поплавка меняется), ожидание конкретного состояния UI —
  вместо постоянного вслепую кликанья. Точка проверки и клик — разные точки: можно смотреть на
  один индикатор, а кликать в другом месте (или туда же, если совпадает). Через `nut-js`
  `screen.colorAt()` — читает реальный пиксель экрана, поэтому работает с любым приложением/игрой,
  не только с этим окном
- **последовательность точек** — клик по очереди в нескольких местах, точки видно на экране
  пронумерованными синими кружками, пока настроен режим «Последовательность» (на всех мониторах)
- **профили настроек** — сохранить/применить пресет под конкретную игру
- **экспорт/импорт** — через нативные диалоги «Сохранить как…» / «Открыть» (не браузерный blob-трюк,
  как в расширении — тут по-настоящему выбираешь путь на диске)
- **запись макросов** — жмёшь «Начать запись», кликаешь и/или печатаешь реальными кликами и
  нажатиями клавиш где угодно на экране, жмёшь «Остановить» (кнопкой или хоткеем `F10`, работает
  даже если окно приложения не в фокусе) — сохраняется точная последовательность (мышь + клавиатура)
  и тайминг, воспроизводится один в один через `nut-js`. При сохранении задаёшь число повторов
  (1-50) — макрос воспроизведётся подряд нужное число раз за один запуск. Кнопка «✎» у уже
  сохранённого макроса открывает переименование и смену числа повторов без повторной записи.
- **отложенный старт** — «начать в 14:30» (один раз), «каждый день в это время» или «каждые N минут»
  (оба варианта сами себя перезаводят после каждого срабатывания — работают, пока не нажать
  «Отмена»)
- **цепочка макросов** — во вкладке «Макросы» отмечаешь галочками нужные и жмёшь «Играть отмеченные
  по порядку» — сыграют один за другим в порядке списка, каждый со своим сохранённым числом повторов
- **дождаться текста** — вкладка «Клик»: выделяешь область экрана (та же рамка, что у OCR) и
  задаёшь ожидаемый текст — кликает только когда этот текст появляется в области (проверяется через
  OCR раз в 1.5 сек, не на каждый клик — иначе слишком тяжело). Как триггер по цвету, но по тексту:
  для ожидания конкретной надписи/состояния UI, а не только цвета пикселя
- **бинды** — вкладка «Бинды»: задаёшь глобальный хоткей и текст, и по нажатию этого хоткея (в любом
  окне Windows, не только в этом приложении) программа сама печатает заданный текст в то поле, где
  сейчас курсор — через `keyboard.type()` из `nut-js`. Только desktop-версия: в браузерном расширении
  таких произвольных глобальных хоткеев технически не сделать (Chrome требует статически прописывать
  все команды в `manifest.json`, добавлять их на лету нельзя).
- **текст с экрана (OCR)** — вкладка «Текст с экрана»: выделяешь мышью любую область на любом из
  мониторов (та же рамка выделения, что и для триггера по цвету), область захватывается через `nut-js`
  `screen.captureRegion()` и распознаётся через [tesseract.js](https://www.npmjs.com/package/tesseract.js)
  (чистый JS+WASM, без нативной пересборки под Electron). Работает с текстом в играх, документах,
  видео — с чем угодно, что реально отрисовано на экране. Язык — русский/английский/оба, выбирается
  в настройках вкладки. **Первое распознавание на каждом языке требует интернет** — tesseract.js
  скачивает языковые данные (`.traineddata`, несколько МБ) с CDN и кеширует их в папке приложения
  (`userData/tessdata`), дальше работает офлайн.
- **запись экрана** — вкладка «Запись экрана»: «Начать запись» → «Остановить» → файл в папке данных
  приложения (кнопка «Открыть папку с записями» рядом). Два режима на выбор:
  - **Таймлапс** (по умолчанию, надёжный) — кадры снимаются по одному через `nut-js`
    `screen.captureRegion()` (тот же механизм, что и у OCR/цвет-триггера), в `.mp4` собираются через
    [ffmpeg-static](https://www.npmjs.com/package/ffmpeg-static) (готовый бинарник ffmpeg внутри
    npm-зависимости, ставить отдельно ничего не нужно). Не плавное видео — реальный темп захвата
    обычно 2-4 кадра в секунду (полноэкранный снимок — тяжёлая операция), по сути таймлапс.
  - **Видео** (экспериментальный) — настоящий видеопоток через `getDisplayMedia()` + `MediaRecorder`
    прямо в рендерере, плавно и с реальным fps экрана (проверено вживую — реально пишет честные
    60 fps, не только теоретически). Раньше такой же класс API (через устаревший
    `getUserMedia`+`chromeMediaSourceId`) на одной из тестовых машин подвешивал процесс намертво во
    время самого захвата — современный `getDisplayMedia` + `setDisplayMediaRequestHandler` в этой
    сессии такого не показал, но раз уже наступали на эти грабли — оставлен режим «Таймлапс» рядом
    как проверенный запасной вариант, а не тихая замена.

  Дополнительно: выбор монитора (если их несколько), обратный отсчёт 3-2-1 перед стартом, красный
  индикатор «REC» поверх экрана, пока запись идёт (свой отдельный HUD, независимый от счётчика
  кликов), и опция «Записывать системный звук» — только в режиме «Видео», через `audio: 'loopback'`
  у Electron.
- **триггер по картинке** — вкладка «Клик»: выделяешь мышью область экрана (та же рамка, что у OCR
  и триггера по тексту) — она сохраняется как образец, и клик срабатывает только когда этот образец
  снова появляется на экране (проверяется раз в 1.5 сек, порог совпадения настраивается ползунком
  50-100%). Как триггер по тексту, но по картинке в целом — годится для иконок, индикаторов, кнопок,
  которые OCR не распознает как текст. Технически интереснее, чем кажется: `nut-js` v4 **не умеет**
  искать картинку на экране «из коробки» — это вынесено в отдельный ImageFinder-провайдер, а готового
  провайдера ни под этот форк (`@nut-tree-fork/*`), ни под оригинальный (`@nut-tree/*`) на npm не
  существует (проверено вживую — `screen.find()` падает с `No ImageFinder registered`, пока такой
  провайдер не зарегистрирован). Официальный `@nut-tree/template-matcher` строится на opencv4nodejs
  (тяжёлая нативная зависимость, риск сломать обфусцированную сборку) и тоже не опубликован. Поэтому
  здесь — свой матчер на [jimp](https://www.npmjs.com/package/jimp) (`image-finder.js`), без единой
  нативной зависимости: грубый проход по уменьшенной картинке ищет область-кандидата, затем точное
  сравнение по трём цветовым каналам (не по яркости — иначе однотонные, но разноцветные образцы,
  например чистая заливка, путаются между собой) в небольшом радиусе вокруг неё. Полный поиск по
  экрану 2560×1440 занимает ~0.1-0.2 сек — укладывается в 1.5-секундный интервал опроса с запасом.
  Протестировано вживую: реальный захваченный образец находится на экране (confidence ~0.99), а
  заведомо отсутствующая картинка корректно не находится (`screen.find()` действительно отклоняет
  промис — раньше была ошибка именно здесь: nut-js **не проверяет** поле `MatchResult.error`, и
  «мягкий» отказ через это поле резолвился как настоящее совпадение).
- **хоткей у макроса** — при сохранении/редактировании макроса можно задать личный глобальный хоткей
  (поле рядом с числом повторов) — макрос проигрывается сразу по нажатию, без захода в приложение и
  без «Играть отмеченные». Проверено вживую: реальное нажатие комбинации через ОС воспроизводит
  сохранённый макрос (клик/нажатие клавиши) один в один.
- **аварийный хоткей теперь глушит всё разом** — раньше `F9` (настраивается) только останавливал
  автокликер, теперь дополнительно прерывает активную запись экрана (оба режима — «Таймлапс» и
  «Видео»), с тем же сохранением файла, что и обычная кнопка «Остановить». Для ситуации «нужно всё
  выключить прямо сейчас», не тыкая по вкладкам.
- **Telegram-уведомления при срабатывании триггера** — отдельная галочка в настройках Telegram:
  помимо старта/остановки кликера, шлёт сообщение и когда сработал триггер по цвету, тексту или
  картинке (по фронту «не было → появилось», не на каждый успешный тик — иначе спам).
- **буфер обмена** — вкладка «Буфер обмена»: последние 50 скопированных текстов (опрос
  `clipboard.readText()` раз в секунду — в Electron нет события «буфер обмена изменился»), с кнопкой
  «Копировать» у каждой записи, чтобы вернуть её обратно в буфер. Можно выключить в самой вкладке,
  если не нужно.

## Лицензия — общая с браузерным расширением

Публичный ключ в `license.js` — тот же самый, что в `extensions/clicker/license.js`. Значит:
**один лицензионный ключ, выданный `extensions/clicker/license-tools/generate-license.js`, открывает
Pro и в расширении, и в desktop-версии.** Ничего отдельно генерировать не нужно — тот же скрипт,
тот же процесс продажи: покупатель донатит от 200 ₽ на
[donationalerts.com/r/leonidbiceps111](https://www.donationalerts.com/r/leonidbiceps111), указав
почту в комментарии к донату → проверяешь донат в личном кабинете DonationAlerts → `node
generate-license.js "покупатель" 30` → ключ высылаешь на присланную почту вручную. Кнопка «Задонатить
и получить Pro» в разделе Pro (и в расширении, и в desktop-приложении) ведёт на эту же страницу.

## Защита от взлома и шаринга ключей — честно про границы

Важно понимать сразу: **клиентский JS в Electron нельзя сделать по-настоящему невзламываемым** — при
желании код всегда можно распаковать (`asar extract`) и отредактировать. Это не недоработка именно
этого проекта, а фундаментальное свойство любого офлайн-приложения без сервера-валидатора. Дальше —
что реально сделано и зачем:

- **Привязка лицензии к конкретному компьютеру (опционально).** В разделе Pro есть поле «ID этого
  компьютера» с кнопкой копирования — отпечаток из hostname + MAC-адресов сетевых карт, захэшированный
  в короткую строку (`getMachineId()` в `license.js`). При продаже можно (не обязательно) попросить
  покупателя прислать этот ID и передать его четвёртым аргументом в `generate-license.js` — тогда ключ
  сработает только на этом компьютере, шаринг ключа другу становится бесполезен (desktop-приложение
  на другой машине честно откажет с сообщением «ключ привязан к другому компьютеру»). Без этого
  аргумента ключ обычный, без привязки — так проще, но и делиться им ничего не мешает.
  **Важно:** привязка к железу работает только в desktop-версии. В браузерном расширении так сделать
  нельзя (песочница не даёт доступа к железу) — там ключ с `machineId` в payload всё равно сработает
  где угодно, потому что расширение это поле просто не проверяет. Проверено вручную: сгенерировал три
  тестовых ключа (без привязки / привязан к чужому ID / привязан к этому компьютеру) — все три ведут
  себя ровно так, как задумано.
- **Обфускация перед сборкой `.exe`.** `npm run dist` прогоняет код через `javascript-obfuscator`
  (переименование в hex, string-array с base64, мёртвый код) — вместо «открыть main.js в блокноте и
  убрать одну строчку» нужно реальное реверс-инжиниринг усилие. Это поднимает планку против
  казуальных попыток, но не остановит того, кто действительно настроен разобраться — это тоже
  честная граница, не обещание неуязвимости. **`controlFlowFlattening` и `selfDefending`
  сознательно отключены** (см. `scripts/build-obfuscated.js`) — у обеих задокументированы баги
  именно такого рода: намертво зависающий процесс на некоторых устройствах без возможности
  воспроизвести на других. Ровно с этим столкнулись на реальном железе пользователя (v2.1.0 и
  раньше) — рабочее приложение важнее той небольшой прибавки к барьеру взлома, которую эти две
  опции давали.
- **Крипто-часть (подпись ключа) при этом реально надёжна** — ECDSA P-256, подделать валидный ключ без
  приватного `private-key.json` невозможно. Слабое место всегда не в математике подписи, а в том, что
  саму ПРОВЕРКУ (`if (result.valid) ...`) в теории можно вырезать из клиентского кода — обфускация и
  привязка к железу как раз про то, чтобы это было максимально неудобно и невыгодно, а не про то, чтобы
  сделать это невозможным.

## Известные ограничения (MVP, не баги)

- Захват произвольной клавиши покрывает основные клавиши 105-клавишной US-раскладки (буквы, цифры,
  F1-F24, стрелки, Numpad, пунктуация, модификаторы) — таблица в `keymap.js`; совсем экзотические
  клавиши (мультимедийные и т.п.) там не сопоставлены и по умолчанию упадут на Space.
- Воспроизведение макроса всегда кликает левой кнопкой — тип кнопки при записи не сохраняется.
- Максимальная пауза между событиями макроса при воспроизведении — 3 секунды (если в реальности между
  действиями было, скажем, 2 минуты паузы, она не повторится — это защита от случайно «зависшего»
  воспроизведения).
- Число повторов макроса ограничено 50 — сознательно нет варианта «бесконечно»: воспроизведение сейчас
  ничем не прерывается на лету (нет отдельной кнопки «Стоп» именно для проигрывания макроса), поэтому
  бесконечный цикл было бы нечем остановить, кроме перезапуска приложения.
- «Редактирование» макроса — это переименование и смена числа повторов, а не покадровый редактор
  событий (нельзя удалить/подвинуть отдельный клик или нажатие клавиши внутри уже записанного
  макроса) — для этого нужно перезаписать заново.
- HUD-счётчик кликов и выбор точки показываются только поверх основного контента — если игра
  запущена в эксклюзивном полноэкранном режиме (не Borderless), оверлей может не быть виден поверх
  неё (ограничение Windows, не этого кода).
- Антивирус/Windows Defender может насторожиться при первом запуске незнакомого `.exe`, который
  симулирует ввод и перехватывает глобальные события клавиатуры/мыши (для записи макросов) — это
  ожидаемо для инструментов такого класса, не баг конкретно этой сборки.
- **Автозагрузка** видит и переключает только записи текущего пользователя (`HKCU`) — записи «для
  всех пользователей» (`HKLM`, общая папка автозагрузки) требуют прав администратора и здесь
  сознательно не показываются.
- **Текст с экрана**: проверено вживую — захват работает для обычных окон/игр/документов, но **не
  умеет захватывать собственное окно МультиТула** — область с текстом самого приложения
  распознаётся как пустая. Это подтверждено не только через `nut-js`, но и независимо через `.NET
  Graphics.CopyFromScreen` (тот же классический подход к захвату экрана) — то есть это не баг именно
  этого кода, а особенность того, как конкретно это Electron-окно рисуется на этой машине. Отключение
  аппаратного ускорения (`app.disableHardwareAcceleration()`) эту проблему не решило — точную причину
  не докапывались дальше, поскольку реальный сценарий использования (распознать текст в игре, документе,
  другом приложении) от этого не страдает.
- **Запись экрана**: режим «Таймлапс» — не плавное видео, реальный темп захвата обычно 2-4 кадра в
  секунду (см. выше). Оба режима сознательно сохраняют файл в папку данных приложения, а не в
  системную папку «Видео» — на машине, где это тестировалось, был включён "Controlled folder
  access" в Защитнике Windows (частая настройка по умолчанию), который молча блокирует запись файла
  от малоизвестного `.exe` (в данном случае `ffmpeg.exe`) в защищённые системные папки (Видео,
  Документы, Изображения, Рабочий стол) — ffmpeg получал "No such file or directory", хотя папка
  реально существовала и была доступна. Папка данных приложения в этот защищённый список никогда не
  входит, так что это не костыль под одну машину, а осознанный выбор понадёжнее. Режим «Видео»
  сохраняет `.webm` (кодек VP9, как отдаёт `MediaRecorder`), не `.mp4`.
- **Привязка к окну** и **дождаться текста** относятся только к автокликеру (клик по таймеру/точке) —
  не к макросам и не к биндам.
- **Цепочка макросов** проигрывается от начала до конца без паузы между элементами — отдельной кнопки
  «Стоп» именно для цепочки нет (как и для одиночного макроса, см. выше про число повторов).
- **Выбор монитора для записи**: режим «Таймлапс» не может записать монитор, расположенный левее
  или выше основного в раскладке нескольких экранов (отрицательные координаты в общем виртуальном
  рабочем столе) — `nut-js` `captureRegion()` отклоняет такие координаты («x coordinate outside of
  display»), проверено вживую. Для такого монитора доступен только режим «Видео» (`desktopCapturer`
  этого ограничения не имеет) — интерфейс сам это подсказывает в названии монитора в списке.
- **Автостарт при простое**: логика простая и стандартная (`powerMonitor.getSystemIdleTime()` ≥
  порог → старт, один раз за период простоя). Изначально не удавалось до конца проверить вживую —
  тестовая машина показывала непрерывную активность (idle time не поднималось выше 0 за 12 секунд
  наблюдения), но позже в этой же сессии сработало само по себе: приложение было найдено уже
  запущенным со 109 накопленными кликами после реального простоя — так что механизм подтверждён
  рабочим, просто зависит от того, действительно ли машина простаивала на момент проверки.
- **Триггер по цвету/тексту/картинке считывается один раз при старте кликера** — изменение области,
  образца или порога совпадения во вкладке «Клик», пока кликер уже запущен, не подхватится на лету
  (опрос продолжает использовать то, что было на момент нажатия «Старт»); нужно остановить и снова
  запустить кликер, чтобы новые настройки триггера применились.
- **Триггер по картинке** — свой матчер (`image-finder.js`) ищет образец «как есть»: не устойчив к
  изменению масштаба или повороту (если элемент на экране изменил размер — например, окно
  игры/приложения переключилось в другое разрешение — образец нужно переснять) и находит только
  первое/лучшее совпадение за проход, а не все вхождения картинки на экране сразу. Проверено вживую:
  надёжно находит образцы с реальной текстурой/контрастом (иконки, кнопки, индикаторы — confidence
  ~0.99), но на почти однотонных областях (пустые обои, плоская заливка без деталей) уверенность
  заметно ниже (в одном тесте — 0.744 против порога 0.9 по умолчанию) — это общее свойство любого
  корреляционного сравнения картинок, не специфичный баг этой реализации: чем меньше в образце
  реальных деталей/границ, тем менее уверенно совпадение. Для надёжного триггера выбирай образец с
  чётким контуром или контрастной деталью, а не однородный кусок фона.
